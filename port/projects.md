# Project Scan Map — where to find what, per project

## Resolving the workspace (machine-independent)

Not every machine has the multi-instance setup — resolve the project's checkout at runtime, don't assume a path:

1. Look under the machine's projects root (usually `~/Projects`) for, in order of preference: `<name>-0` (canonical instance on multi-instance machines), `<name>` (single-checkout machines), then any `<name>-N`.
2. Verify the candidate is the right repo (`git remote get-url origin` matches the project) before scanning. Adanim's origin is `github.com/modstudio/adanim.git`; its `package.json` name is `adanim-monorepo`.
3. All numbered instances are parallel checkouts of the same repo — scan exactly ONE, and always `git fetch` and read from `origin/<default-branch>` so the local checkout's state doesn't matter.
4. If no checkout exists on this machine, say so and stop — don't clone.

Default branches: starship/stopal/alephbeis `develop`; **adanim `master`** — single-branch, no develop, so there is no feature→develop→master train and doctrine #6's squash-merge assumptions apply directly to `master`.

> **Adanim moved under this skill's feet (verified 2026-08-11).** It was added as `shulbase` on 2026-07-31 with no git remote; it has since been **renamed to adanim**, gained the origin above, and **restructured `apps/api/src/modules/*` into `contexts/*` + `kernel/*`**. Every adanim path below reflects the new layout. Task keys are `ADN-*`. If a future run finds these paths missing, re-survey rather than assume — this project is moving fast.

### 2. Workflows (dev flows: plan-task / ship-task / code-review / sync-docs / release …)
Definitions live in each project's DB; edited via `*workflow*` MCP tools; composed via ComposeWorkflow. Starship+alephbeis have the identical 13-tool surface (steps + modes + compose).
- **starship**: `app/Domains/Infrastructure/Mcp/Workflows/` (Models/Repos/Composer+Resolver/Commands/AgentTools/Prompts — active workflows registered as MCP prompts by `StarshipServer::buildWorkflowPrompts()`); MCP `Tools/Workflows/`; HTTP `Api/Mcp/McpWorkflow*Controller` + `WorkflowPreferenceController` (per-user autonomy/release_depth prefs).
- **stopal**: `apps/api/src/modules/workflows/` (service/router/schemas/mcp; MCP prompt registered too); DB `packages/db/src/schema/workflow.ts`; UI `apps/web/src/app/ops/workflows/`.
- **alephbeis**: `app/Domains/Workflows/` (Models/Composer+Resolver/ComposedPrompt); seeded from JSON `database/seeders/workflows/*.json` via `WorkflowsSeeder` (idempotent by slug); MCP `Tools/Workflows/`; HTTP `Workflows/WorkflowAdminController`; UI `workspace/workflows/`.
- **adanim** — **code-declared, not DB-backed: the fourth distinct approach.** `apps/api/src/kernel/workflow/` (`workflow.{router,service,types,test}.ts` + `workflows/{plan-task,ship-task}.ts`). Workflows are typed TS modules in a `WORKFLOWS` array, not rows — so there are no create/update/delete workflow MCP tools, no seeder, and no admin UI; a workflow changes by editing code and shipping it. `validateWorkflows()` runs at load and **rejects structurally incoherent definitions rather than letting them fail silently** — e.g. more than one default mode, or an `entry` question declared beside a default mode that would make the question unreachable. `.agents/workflows/code-review.md` still exists as a prose workflow alongside.
  Consequences for porting: a change to another project's *workflow content* (step text, modes, autonomy knobs) translates fine; a change to its *workflow management surface* (the 13 MCP tools, admin CRUD, per-user prefs) has no landing site and should be dropped, not staged. Porting **outward**, the load-time validation is the transferable idea — the DB-backed three can only discover the same incoherence at compose time, if at all.

### 3. Rulebook / canon system (DB-sourced rules → generated agent files)
- **starship**: domain `app/Domains/Infrastructure/Mcp/Rules/`; MCP `Tools/Rulebook/` (+GetSessionRules); HTTP `Api/Rules/RuleController` (`/api/rules/{bootstrap,export}`, reorder; token abilities canon:read/write); hydrate `scripts/sync/hydrate.sh` → `.agents/rules|reference` → per-tool copies via `scripts/sync/agents.sh`; SessionStart hook `scripts/hooks/claude-session-rules` (+ `claude-edit-guard`); integrity `scripts/canon/check-canon-integrity.php`; nightly `canon-sync.yml`; LLM canon evals `app/Domains/Infrastructure/AI/CanonEvals/` + `nightly-canon-evals.yml`.
- **stopal**: file-based, no DB rulebook (workflows are the DB-backed analog) — but now a **two-tier canon**: always-on `.agents/rules/00..30-*.md` plus a path-scoped reference tier `.agents/reference/*.md`, reached by Claude Code's native loader through the `.agents/rules/reference` → `.claude/rules/reference` symlink. Generated to `.claude/` etc. by `scripts/sync/agents.sh`. Three guards, all for silent failures: `scripts/check-canon-scoping.ts` (**a reference doc missing its `paths:` frontmatter does not fail to trigger — it silently rejoins the always-on tier**, putting ~240k back into every session with nothing in the diff that looks wrong), `scripts/check-canon-rot.ts` (+ its test), and the domain-glossary ratchet `scripts/check-retired-terms.ts`. Also `check-doc-task-keys.ts` / `check-task-keys.ts`.
- **alephbeis**: domain `app/Domains/Canon/` (Rule model, parser/assembler, reorder job); MCP `Tools/Rulebook/` (+GetSessionRules); HTTP `Canon/RuleController`; export via `php artisan canon:sync` (`SyncCanonCommand`); `.claude/` is a symlink farm into `.agents/` (CLAUDE.md → .agents/AGENTS.md); seeder `RulesCanonSeeder`.
- **adanim**: file-based, no DB rulebook and no GetSessionRules. **Two-tier canon**: always-on `.agents/rules/{00-system-prompt,01-core-workflow,05-domain-glossary,10-coding-style,15-security,20-architecture,30-testing,40-design-system}.md`, plus **path-scoped context docs** `.agents/contexts/{design-system,luach,quire}.md` that load only for sessions working in the code their frontmatter `paths` claims (mirrored at `.agents/rules/contexts`). This is the same two-tier shape stopal arrived at — same platform mechanism (frontmatter `paths:` + a symlink into `.claude/rules/`), different tier name (`contexts` vs `reference`). **Diff the two before porting canon work in either direction; neither is the origin of the idea.**
  Two gates, both worth porting outward: `scripts/check-rules.ts` (`bun run lint:rules`) enforces the machine-checkable slice of the rules, and **`scripts/check-canon.ts` verifies the canon is still TRUE, not merely present** — it catches a context doc that no longer loads (symlink gone, frontmatter lost its `paths`), one that loads but claims paths that no longer exist, and any canon file naming a path/command/task-status/identifier the tree no longer holds. That third check covers every tier including workflow prompts, on the reasoning that an unconditionally-read instruction is *more* expensive when wrong, not less.
  **The two canon guards divide the same problem differently and neither is a superset** — stopal's `check-canon-scoping.ts` protects the *tier split* (does the doc still scope itself, or has it silently rejoined always-on) while adanim's `check-canon.ts` protects *truthfulness* (does the doc still describe a tree that exists). Stopal's `check-canon-rot.ts` overlaps the second. Starship's `check-canon-integrity.php` is narrower than both. The honest port here is a merge, not a copy — read all three before staging.
  **`check-rules` checks the WHOLE TREE, not the diff** — a deliberate departure from the diff-ratchet philosophy the other three share (§10), on the grounds that the tree is already clean so a diff-only net would let files drift back. Do not "fix" it into a ratchet when porting quality-gate work; porting a ratchet *to* adanim means arguing the case first.
  Note `contexts/luach` and the `rule_*` MCP tools are **product** (Hebrew-calendar occasion rules), unrelated to canon — never scan them as rulebook changes.

### 7. MCP server infrastructure
- **starship**: `Servers/StarshipServer.php` (~55 tools + dynamic workflow prompts); `routes/ai.php` `Mcp::web(... auth:sanctum)`; token minting `app/Domains/User/ApiToken/` + `Infrastructure/ServiceAccount/` (service-account tokens) with **fine-grained token abilities** (`mcp`, `canon:read`/`canon:write`, `beacon:file`) — the most granular scoping of the four; `Support/{ReadOnlySqlGuard,QcDatabaseTunnel}`; audit domain `Infrastructure/Audit/` (domain-change audit — NOT per-MCP-call); launchers `scripts/mcp/`.
- **stopal**: `lib/mcp-server.ts` (`buildMcpServer`, `runTool` envelope, `assertPrivilege`, DomainError mapping); `routes/mcp.ts` (stateless streamable HTTP, rate-limit → auth → handle); `lib/mcp-auth.ts`; `lib/rate-limit.ts` (600/min); token minting `modules/access-tokens/` + ops UI (`/app/account/access-tokens`); privileges engine `lib/privileges.ts` + `schema/privilege.ts`; `routes/oauth-metadata.ts`.
- **alephbeis**: `Servers/AlephbeisServer.php` (~46 tools); `routes/ai.php` with `[McpAuditMiddleware, auth:sanctum, ability:mcp, throttle:mcp]` (audit first so 401/403 are recorded); token minting `app/Domains/Person/ApiToken/` (single `mcp` ability).
- **adanim** — **the reflection design; the deepest MCP thinking of the four and the main reason to port FROM here.** `kernel/mcp/` maintains no tool list at all: `mcp.service.ts` reflects the tRPC router (`trpc/router.ts`) into MCP tools, so every procedure becomes a tool automatically, its Zod input becomes the tool's inputSchema, and calls run through the normal tRPC caller under the resolved context — **every permission check applies exactly as in the app, with no parallel authorization path to drift**. Exposure is **opt-in per procedure** via `meta.mcp` (`McpToolMeta = true | 'confirm'`) — there is **no `DENY` set** and never was one (verified 2026-08-24: `git log -S'DENY'` over `kernel/mcp` returns nothing). The stated reason for opt-in: otherwise a procedure becomes callable by a token holder as a side effect of being written, "which is how sending, deleting and revoking arrived on the surface without anybody choosing them". Around that core:
  - `mcp.election.ts` + `schema/mcp-election.ts` — a caller can **pin where their tools run** (`local` | `production`, scoped `session` | `platform`, lapsing). The design point worth carrying: the switch is the caller's but the reachability is the deployment's, so a pin is only honoured by a deployment that can actually forward — a pin can never silently mean nothing.
  - `mcp.forward.ts` — the forwarding itself; `mcp.route.ts` — routing; per-caller visibility is `publishedCatalog()`/`couldPass()` in `mcp.service.ts` + `trpc/index.ts` (`mcp.visibility.ts` is the TEST, not the implementation); `mcp.catalog.test.ts`; `CONFIRM_KEY`/`PRODUCTION_CONFIRM` gate destructive production calls behind explicit confirmation.
  - `schema/mcp-call.ts` — **per-call MCP audit logging**, the same idea as alephbeis's `McpAuditLogger` arrived at independently; diff the two before porting either direction.
  - `scripts/mcp-router.ts` + `scripts/mcp-catalog.ts` front several deployments behind ONE registered server and one tool list.
  Token minting `lib/api-token.ts`; authz `lib/authz.ts` (+ `authz.operator.test.ts`, `schema/operator-read.ts`) + `packages/shared/src/permissions.ts`. Tools surface as `mcp__adanim__<namespace>_<procedure>`.
  Porting the reflection outward is an architectural change, not a feature copy: it only pays off where the app's own call layer already carries authorization (stopal's tRPC is the natural fit; the Laravel pair would need their HTTP/action layer reflected instead). Weigh it as a design proposal, never stage it as a mechanical port. The election/forward/confirm pieces, by contrast, port as ordinary features.

### 11. Multi-instance / dev environment

### 12. App config system (DB-backed, encrypted, runtime-resolved)
- **starship**: `app/Domains/Infrastructure/Configs/` (AppConfig model, service, repo, IP-allowlist provider); typed key enums `Configs/Keys/*ConfigKey.php` (10 providers — set is per-project).
- **stopal**: `apps/api/src/modules/app-config/` (environment cascade all/production/staging/local; `PUBLIC_CONFIG_KEYS` allowlist for unauthenticated getPublic); crypto `packages/db/src/lib/config-crypto.ts` (encrypt/reEncrypt/mask, `CONFIG_ENCRYPTION_KEY`); ops UI `ops/configs/`; SPA resolves analytics config at runtime (no build args).
- **alephbeis**: `app/Domains/Console/Config/` (AppConfig with per-value `is_secret` encryption + cross-env re-encryption; `ConfigWiringService` pushes DB config into Laravel config at boot; typed enums `Enums/ConfigKeys/`; Set/Get/Cache artisan commands).
- **adanim**: `apps/api/src/kernel/app-config/` + `packages/db/src/schema/app-config.ts`; per-environment values (`Environment` type), encrypt/decrypt in `@app/db`, runtime reads via `getAppConfigValue` while the module is the admin write side. **A secret's value is never returned by `list`** — only a masked hint identifying WHICH secret is stored, explicitly so the config screen can't be used to read secrets back. UI on the superadmin surface; MCP `appConfig_{list,set,remove}`. Closest sibling is stopal's `modules/app-config/`; the notable gap vs stopal is no `PUBLIC_CONFIG_KEYS` unauthenticated-read allowlist.

### 13. Sync / release / dev scripts
Starship, stopal and alephbeis share the same `scripts/sync/` fabric (main + lib/config/agents/mcp/ops modules, driven by `.agents/config/sync-config.yml`) — generates per-agent-tool configs and `.mcp.json`. **Adanim has none of it** (see below), so sync changes have no landing site there until the fabric itself is ported.
- **starship**: adds `--hydrate` (canon from DB); worktree fabric per section 11; release = atomic deploy `ci/{setup_atomic_release_layout.sh,atomic_deploy.sh}` + `scripts/ops/setup-branch-protection.sh` + `scripts/ci/`.
- **stopal**: per-tool MCP emitters `scripts/sync/mcp/*.sh`; `scripts/release.sh` (flyctl staging/prod, CI-parity gate, per-app change detection, `[cli-release]` marker); git-event ingestion `modules/git-events/` + `routes/github-webhook.ts` (HMAC; links commits/PRs to tasks by issue key).
- **alephbeis**: per-tool MCP emitters `scripts/sync/mcp/{claude,codex,cursor,gemini,junie,warp,windsurf,zed}.sh` (documented `docs/tooling/sync.md`); schema-validation tooling `scripts/validation/` + `app/Infrastructure/MigrationValidation/` + `ValidateReleaseMigration`; `scripts/check-dependency-freshness.php`.
- **adanim**: **still no `scripts/sync/` fabric** — agent-tool config is not generated; `.agents/` is authored directly and `CLAUDE.md`/`AGENTS.md` sit at the repo root as real files. But `scripts/` is no longer thin: alongside the gate suite (§10) it carries `worktree.ts` (worktree management), `merge.ts` (`bun run merge`), `status.ts`/`status.lib.ts` (`bun run status`), `deploy-guard.ts`/`deploy-status.ts`, `mcp-router.ts`/`mcp-catalog.ts`, `generate-fonts-css.ts`, `pull-config.sh`. Skills are vendored with `skills-lock.json` + `.agents/skills/` — a lockfile approach none of the other three use, and a small candidate to port outward. Release is `bun run deploy` → guard + `fly deploy` per app (`GIT_SHA` build arg); no atomic-deploy layout, no branch protection, no git-event ingestion.

## Reference implementations (deepest instance = default port source)
- Task hierarchy/links/mentions, KB, code metrics, Beacon monitoring, canon evals, atomic deploy, fine-grained token abilities, **worktree-per-task with a database per worktree (ports, session cookie, teardown/sweep)**: **starship**
- Ops dashboard/backups UI, access-token minting + privileges, git-event→task linkage, runtime public-config, release.sh CLI-deploy: **stopal**
- MCP audit logging, workflow JSON seeding, schema-validation tooling, instance-info script, architecture-naming tests: **alephbeis**
- tRPC→MCP tool reflection (one authorization path, no hand-maintained tool list), deployment election + forwarding + production-confirm, per-call MCP audit, the destructive-call **acknowledge** gate (bare call = preview), code-declared workflows with load-time validation, canon-truthfulness gate, `kernel`/`contexts` boundary check, vendored-skills lockfile, **migration-lineage fork check at merge**: **adanim**
- **Worktree hooks** (`WorktreeCreate`/`WorktreeRemove` replacing built-in creation so a worktree arrives ready): **starship and adanim independently** — starship's is far deeper (database, serving, sweep); adanim's worktrees deliberately **share one Postgres**, with a ring of diagnostics around that one failure mode. Neither is the origin; diff before porting either way.
- Two-tier canon (always-on rules + path-scoped reference/context docs) and its scoping guard: **stopal and adanim independently** — no single origin; merge rather than copy.

Adanim imports and exports in different categories rather than being uniformly behind. **Missing** (greenfield if targeted — check the user wants the weight): CI, KB/documents, code metrics, system monitoring, agent ops tools, sync fabric, multi-instance support. **Ahead** (worth scanning as a source): the MCP layer (§7), code-declared workflows with load-time validation (§2), the canon-truthfulness gate (§3), and the gate-enforced `kernel`/`contexts` boundary (§10).

MCP task-creation for target tasks: starship `create-task-tool` (verb-first `*-tool` names), stopal `task.create` (dot-named, appears as `mcp__stopal__task_create`), alephbeis `create-task-tool` (appears as `mcp__alephbeis__create-task-tool`), adanim `task.create` (reflected from tRPC, appears as `mcp__adanim__task_create`).

Adanim task fields differ from the other three: statuses are `backlog|todo|in_progress|blocked|done` (**`blocked` is adanim-only; there is no `in_review` or `canceled`**), priority is `low|medium|high` (no `highest`), and `labels` is a plain text array rather than a tag entity — so there is no category or tag model to map onto. It **does** have projects and per-project keys (`project.key` + `nextNumber` → task `key`), but **no parent/child hierarchy**. It also carries provenance the others lack — `filedBy` / `filedFromOrg` / `filedFromSkill` / `hasConversation`, recording that a task was filed from an AI-assistant conversation (`agent_fileFeatureRequest`). Check the Zod schema at run time rather than assuming the stopal shape; the tool list is reflected, so the schema is always current.
