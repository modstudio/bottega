# Backports — improvements to feed back to other projects

Running list of places where a port (or any implementation work) deliberately improved on another project's implementation. Each entry is a pending port candidate in the OTHER direction — when a port run targets that project, present these alongside the scan results. Implementers append entries here the moment they diverge-to-improve; remove an entry once it's staged as a task in the beneficiary project.

Entry format: `- [ ] <what improved> — <where it lives> (<origin task>). <why the original is worse.>`

## → starship

From stopal's worktree serve work (STO-918 defects found while building STO-920, 2026-08-24):

- [ ] **A free-port probe must BIND, not connect — and must bind the SPECIFIC loopbacks.** Stopal's `portIsFree` dialled `127.0.0.1` and called the port free when nothing answered. Vite (and plenty else) binds `[::1]` ONLY, so the probe reported a port free while a dev server held it — measured: with this worktree's own Vite on `[::1]:4290`, the probe said 4290 was free, so the next worktree would have been handed it. The naive fix is also wrong: binding the WILDCARD (`0.0.0.0`/`::`) does not collide with a listener on a specific address, so a wildcard-only bind probe still reports free — measured `{"0.0.0.0":true,"::":true,"127.0.0.1":true,"::1":false}` for a held port. Correct probe: bind all four of `127.0.0.1`, `::1`, `0.0.0.0`, `::` and require every one; set the socket `exclusive` (else SO_REUSEPORT lets the probe bind alongside a live server); and treat ONLY `EADDRINUSE`/`EACCES` as taken, because a bind that fails for want of an address family (no IPv6) would otherwise report every port busy forever. Directly relevant here: an adanim worktree was holding `[::1]:3200`, which is the port stopal's checkout declares as its own `WEB_PORT` — several projects on one machine allocate dynamically, so a false "free" is exactly how two of them meet.

- [ ] **Assert that an injected per-instance value REACHED the process; do not trust the injection.** Stopal injected a per-worktree cookie prefix and per-worktree ports at launch and shipped believing both worked. Two independent mechanisms severed them, each silent: (a) turbo with `globalEnvMode: strict` strips any variable absent from `globalPassThroughEnv` — proved with a scratch workspace printing `LISTED=[yes] UNLISTED=[]` — so the cookie prefix never reached the API and every worktree silently shared ONE session cookie; (b) the root `dev` script ran `set -a && . .env`, which re-sources the file OVER the injected environment, so every value that also exists in `.env` (the ports) was clobbered and the worktree bound the checkout's ports. Wherever a project injects per-instance identity at launch (ports, cookie/session names, cache key prefixes, DB names), verify it end-to-end against the running process — read the actual `Set-Cookie` name off a real response, read the actual bound port — rather than verifying the code that sets it.

From the 2026-08-24 worktree-tooling port (staged in alephbeis as AB-2418 and children; nothing built yet — revisit once they land):

- [ ] **Extend find/replace body patching beyond canon rules.** `RuleContentPatcher` is wired only into `UpdateRuleAction`, so task descriptions, workflow steps and task documents still replace **wholesale**. That is not merely costly — re-sending a long body from a model's context reconstructs it rather than preserving it, so a dropped paragraph or a silently reformatted table looks exactly like a successful edit. The service itself needs no change — only additional call sites and the `find`/`replace` argument pair on those tools. Surfaced by hitting the cost live: appending one reference line to eleven staged tasks meant resending eleven multi-page descriptions.

A rig that retries where the stack does not is not standing in for the stack, and the drift is silent when it happens. Alephbeis is staging the same service with a note to derive both from one source (AB-2422); whichever project solves it first, the other should take it.

From the stopal collision-safe short-code work (STO-481, shipped 2026-07-20):

- [ ] **`ON CONFLICT DO NOTHING` (arbiter-scoped) beats catch-23505-and-retry for coded inserts inside transactions** — `packages/db/src/coded-insert.ts` (`insertCoded`/`insertCodedMany`). Stopal's writer targets the code column's unique index with DO NOTHING, so a collision raises no error and the **surrounding transaction survives** — no savepoints needed, and conflicts on every other constraint still throw. From the starship short-id collision-safety work (STAR-4600 shipped; STAR-4608 built):

- [ ] **One collision-safe writer for every hash-derived short id** — `App\Modules\ShortId\UniqueShortIdWriter` + a `UNIQUE` index on the durable-key column (STAR-4608, built). Any project generating a short id as `crc32b(uuid)` shares this defect class: the key is an 8-hex value in a 32-bit space, so P(collision) is ~1.1% at 10k rows and grows *quadratically* — ~10% at 30k, ~28% at 53k. Starship had three inconsistent postures at once: `tasks.hash_short_id` had **no unique index and no collision check**, so a collision silently resolved links/mentions/unfurls to the **wrong record**; products retried by **re-rolling the row's UUID**; knowledge articles and task documents had **no handling at all**, so a collision hard-failed creation. Fix converges all four onto one writer that, on a unique violation naming the key column, re-derives the key from the next attempt salt and retries (capped). Two non-obvious design points worth carrying over: (1) the generator's **attempt 0 must stay the bare unsalted hash**, byte-identical to every key ever issued, and pinned by a literal in a test — otherwise a salting change silently re-keys existing rows and breaks live bookmarks; (2) the writer **re-assigns only on retry, never on attempt 0**, because the same `save()` handles updates — re-deriving every call would reset a record that previously escaped onto attempt 1 back to its attempt-0 key, silently moving a durable anchor. Salting was chosen over UUID re-rolling because a task's id is allocated upstream and already carried by events/relations before the write; verify the same before adopting either. Check each project's schema first — in starship every *other* short-id column was already `UNIQUE`, which is what exposed the outlier.

From stopal's port of the merge-lineage check (STO-922, 2026-08-24):

- [ ] **Do the head analysis yourself; `drizzle-kit check` is both slower and narrower than the question.** Stopal ported adanim's `scripts/merge.ts` idea and could not use its mechanism. Two findings, both measured on drizzle-kit `1.0.0-rc.3` (stopal) against `1.0.0-rc.5` (adanim): (a) **rc.3's commutativity analysis is superlinear to the point of hanging** — 110 snapshot folders took 4s, 130 did not finish in 45s, 137 never finished; the same 137 folders read by an rc.5 binary take 0.5s. `generate` runs that same analysis before it diffes anything, which is the real cause of stopal's long-standing "generate spins at 99% CPU" workaround. Adanim is on rc.5 today, so it is not currently exposed — but a `check` shelled out to from a merge command is a gate whose cost is set by a dependency's version, and it hangs silently rather than failing. (b) **`check` answers a narrower question than "is the lineage forked":** it fails only on a NON-COMMUTATIVE fork (two branches touching the same object) and prints "Everything's fine 🐶🔥" for a fork whose statements happen not to collide. Reading `id`/`prevIds` out of each `snapshot.json` and reporting any set with more than one HEAD is ~20 lines, is O(n), takes 0.1s over 137 folders, and names both migrations and their shared parent in the failure.
- [ ] **Ask the merge, not the branch — `git merge-tree --write-tree <base> <head>` gives the post-merge tree with no descendant requirement.** Adanim's command refuses a branch that is not already a descendant, which is what makes reading the branch tip's own tree equivalent to the post-merge state. Stopal cannot require that (feature branches are squash-merged into `develop` behind a review gate, and are routinely behind it), so it hands both refs to `merge-tree` and reads the tree git says the merge produces. It is exact rather than approximate — a union of the two directories cannot express a migration folder the branch DELETED, which is precisely how a lineage grows a parent that is not there — and it needs no rebase first, so the answer arrives while the fix is still cheap. Worth having in adanim too as a pre-rebase question.
- [ ] **A CI checkout of a `pull_request` IS the merge, so the same check needs no git at all there.** GitHub checks out `refs/pull/N/merge`, so reading `packages/db/drizzle` off disk is the post-merge lineage by construction — no fetch depth, no base ref, no merge-tree. Stopal's script takes `--dir` for exactly this and CI spends 0.1s on it.
- [ ] **The lesson that a rebase alone does NOT unfork a lineage, stated in the failure text.** Rebasing moves the commit; the snapshot's `prevIds` still names the old parent, so the fork survives it. Adanim's message says "delete the newer folder and generate it again" and is right to; stopal's spells out `git rebase` **and** `rm -rf <folder>` **and** `db:generate`, because the rebase-only attempt is the obvious first thing to try and it leaves the gate red with no explanation of why.

Checked and found NOT applicable, recorded so it isn't re-raised each run:

- **The hash-derived short-id collision class (→ starship / → alephbeis above) does not reach adanim.** `packages/shared/src/short-id.ts` generates ids **randomly** over Crockford base32 (32⁸ ≈ 1.1×10¹² values) with a unique index plus regenerate-on-conflict, rather than deriving them from a row key — so there is no `crc32b(uuid)` birthday problem to fix. It is arguably the stronger posture and the reasoning is worth reading before staging the writer elsewhere: a derived id is also *reversible and enumerable*, which the random scheme avoids as a side effect. Its two extra constraints (no `I`/`L`/`O`/`U` so ids survive being read down a phone; every id mixes a digit and a letter so it can never collide with a real routed path like `/login`) are adanim-specific product requirements — do not port them outward as general rules.
