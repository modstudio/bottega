# Intentional Differences — what each project keeps unique, and how to translate

Per-project uniques (changes falling here are NOT ported), stack translation notes, and process differences. Update this file the moment the user states a new intentional difference. (The portability test and shared doctrine live in `doctrine.md`.)

## Stack mapping (how to translate, not a reason to skip)

Stacks and layouts are enumerated in `projects.md`; this section is only about translation:

- starship ↔ alephbeis (both Laravel/DDD): porting is near-direct, but respect the layout uniques below — never restructure one to match the other.
- stopal ↔ adanim (both Bun/TS Turborepo, Drizzle, Fly, biome): the closest pair after starship↔alephbeis, and the two are converging independently (both reached a two-tier canon; both log MCP calls). File shape translates near-directly — `<name>.{service,router,schemas}.ts` either way — **but the directory grammar differs and must be honoured**: stopal is flat `apps/api/src/modules/<name>/`, adanim splits `apps/api/src/kernel/<name>/` (portable) from `apps/api/src/contexts/<domain>/<name>/` (product), and that split is gate-enforced by `check-boundaries.ts`. A port into adanim must land on the correct side of it; a port out of adanim must not drag the split into stopal. Authorization also differs — stopal's privileges engine vs adanim's `packages/shared/src/permissions.ts` — so port the rule, not the call.
- to/from stopal or adanim: translate PHP domain code ↔ Bun/TS modules — port the feature/behavior, never the code shape.
- MCP tool style: starship = action classes under `Tools/` + `AgentTools/` (verb-first `*-tool` names); alephbeis = one `*Tool.php` per tool under `Tools/<Group>/`; stopal = co-located `<module>.mcp.ts` registered in `lib/mcp-server.ts` (dot-named `noun.verb`). Ported tools are re-expressed in the target's style. **Adanim is the exception: there is no tool file to write.** Tools are reflected from the tRPC router, so "add an MCP tool" there means "add a procedure" — and the only per-tool knobs are the `DENY` set and the procedure's `mcpEnvironment`. A port that hand-registers a tool in adanim is a port done wrong.
- **Container base image OS differs — apt sources don't translate.** starship's dev/server images are **Ubuntu** (24.04 noble); alephbeis's are **Debian** (`php:8.5-apache-bookworm` → `alephbeis-app-base`). So any Ubuntu-only apt source in a ported Dockerfile change (`add-apt-repository`, `ppa:*` — e.g. `ppa:git-core/ppa` for git ≥ 2.48, `ppa:ondrej/php`) has **no Debian equivalent** and must be re-sourced for Debian (a newer-suite pin, backports where sufficient, or build-from-source). Verify the resulting version actually clears the floor — Debian bookworm/backports often lags the PPA. (First hit: git ≥ 2.48 for relative-path worktrees, AB-2101.)

## Per-project uniques (keep, don't port over/away)

### starship
- Simple/Smart task split (`Workspace/Tasks/{SimpleTasks,SmartTasks}`) — starship-specific model; other projects use a single task flavor.
- Nested MCP location `app/Domains/Infrastructure/Mcp/` — do not restructure to match alephbeis.
- Product-coupled ops tools stay: QueryIms/QueryQcDatabase (Acctivate tunnels), Import tools.

### alephbeis
- Tool-level gaps vs starship are portable candidates, discovered by diffing at scan time — NOT recorded here.
- Flat `app/Infrastructure/Mcp/` + `app/Domains/{Tasks,Workflows}` layout — do not restructure to match starship.
- `app/Domains/Notification` is the **portal-facing** user feed — it is NOT the console/workspace feed. Ported workspace notification features must not silently ride on it; whether console task notifications get their own feed store (starship-style) or merge into the portal feed is a per-feature design decision requiring explicit planning.
- **The YouTrack import carries delivered history *plus* still-live work — but drops not-started and abandoned issues.** Starship's importer keeps only `resolved != null` (pure history; every open issue stayed in YouTrack). Alephbeis widens that by one category only: **unresolved issues that are actively in flight** (`In Progress`, plus the three QA states `Test` / `In QA` / `Waiting for QA`) come across as live board items, because dropping them would strand real current work. Everything not-started (`Open`, `Backlog`) and everything resolved-but-abandoned (`Duplicate`, won't-fix/obsolete) is **not** imported and stays in YouTrack for lookback. Still a **one-time cutover**, not a sync. Consequences vs starship: (a) a real state → board-status mapping is needed rather than "set the completed status", with `Test` never collapsing into `Complete`; (b) carried-over live tasks need correct assignee and `kanban_rank` on the single run; (c) the imported key range is **sparse**, so downstream backfills must treat "no task for this key" as normal, not as an error. Bonus effect: superseded work needs no manual curation — it all sits in `Open` and drops by construction. Also note this instance names the type field **`Category`**, not `Type`, and rejects state-name clauses in the query string (filter client-side).
- **Workspace `Knowledge` KB is internal-docs-only; it deliberately does NOT carry Starship's user-facing `User` audience.** Alephbeis already has `app/Domains/Academy` — a mature user-facing content platform (authoring, categories, versioning, PDF export, `pgvector` embeddings powering AMA RAG). So Starship's `Audience` model (User/Technical/AgentX bound to Buckets) does **not** port: the ported `Knowledge` domain (team-scoped internal docs + agent RAG lookup) has **no audience axis** — just team + category + status, gated by a per-team `kb_enabled` switch. User-facing content stays Academy's concern (author it there, or extend Academy). Keep the two systems distinct — separate domains, tables, retrieval, corpora — they are never merged, and never reintroduce a user-facing audience into workspace Knowledge.

### Container naming diverges by deploy constraint — do NOT converge them
Both projects follow doctrine 7, but land in different places, and each is correct for itself:
- **alephbeis parameterizes** `container_name` as `${INSTANCE_NAME}-*`. Its deploy renames a fixed container during the atomic swap and routes cloudflared at it, so a fixed production name is genuinely required.
- **starship sets no `container_name` at all** (target state of STAR-4622), letting `COMPOSE_PROJECT_NAME` namespace containers. Verified 2026-07-21: its `ci/` has zero `container_name` or `docker compose` references and its deploy is an atomic filesystem-layout swap — nothing pins a name.

Doctrine 7 prefers *no name at all*, so starship's is the better end state; alephbeis's is a constrained fallback, not drift. Neither ports to the other. What DOES port both ways is the **enforcement gate** — the invariant is unenforceable by convention and drifted to 41 occurrences in alephbeis before one existed.

> **Updated 2026-08-24 — the *parallel-checkout* half of this is being retired, the *naming* half is not.** Alephbeis has adopted the one-checkout + worktrees model (epic AB-2418, retirement in AB-2428): once a worktree has its own databases and its own served URL, sibling checkouts have no remaining purpose. **This does not converge the container naming.** `${INSTANCE_NAME:-alephbeis}-*` stays, because alephbeis's atomic-swap deploy renames a fixed container and routes cloudflared at it — that constraint is unaffected by how many checkouts exist. So after AB-2428 the divergence narrows to exactly one thing: starship sets no `container_name`, alephbeis parameterises one for a deploy reason. Still do not converge them. What ports both ways remains the enforcement gate, plus *addressing containers by compose service rather than by name*.

### Two databases change every worktree/dev-env port into alephbeis
Alephbeis runs **both** a legacy MySQL connection and `pgsql`; starship and stopal run one database each. Any ported dev-environment feature that provisions, seeds, migrates or tears down a database must therefore be **doubled**, and a generated env file must carry both `DB_DATABASE` and `DB_PG_DATABASE`. A port that isolates only one connection is worse than none — migrations half-land.

One deliberate asymmetry inside that (decided 2026-08-24, AB-2420): the seed **pricing and budget ceiling apply to the MySQL side only**; `pgsql` is treated as always-full. The pg side is new code and comparatively tiny, so making the agent reason about its size buys nothing. This is an alephbeis-only refinement — it is not feedable back, because neither other project has a second connection.

### stopal
- Web ops UI (`apps/web/src/app/ops/`) — kanban/list/table/task-tree views are stopal's frontend; the Laravel apps don't get these ported 1:1.
- Stripe/figma integrations — product-specific.
- **Sibling checkouts are being retired in favour of worktrees** (ruled 2026-08-24, staged as STO-915/STO-921). stopal follows starship here: `scripts/new-instance.sh` and the `stopal-N` model go once worktree-per-task with a per-worktree database is proven. Do **not** port anything that deepens the sibling-instance model, and do not port adanim's opposite choice — adanim fixes its compose project name specifically so every worktree shares ONE Postgres, which is the design stopal is moving away from.
- **The tRPC→MCP reflection design is NOT wanted** (ruled 2026-08-24). stopal keeps its hand-registered `<module>.mcp.ts` registrars and the resulting duplication with `<module>.router.ts`. Do not re-stage it; the standalone pieces (per-call audit, the acknowledge gate) were taken separately. Re-raise only if asked.
- **No per-user autonomy/release-depth settings** (ruled 2026-07-21, alongside the earlier per-user workflow opt-in deselection): stopal uses TEAM-WIDE defaults baked into the workflow text itself — ship-task's release step declares default depth `master` with an in-session override, and the single pause is the Ship gate (diff review before push). Do not port starship's `WorkflowPreferenceController` / per-user autonomy-knob storage to stopal.

### adanim
- **The task tracker is platform-scoped and single-purpose** — it tracks building Adanim itself, lives in the super-admin space, and deliberately carries no `spaceId`. It is not a product feature for tenant orgs. Never port anything that would make tasks org-scoped or customer-visible.
- **No DB-backed workflow or canon system, by present state rather than by ruling.** Both are absent, not rejected — but staging either is a from-scratch build, so raise it as a proposal and get an explicit yes before creating tasks.
- **`scripts/check-rules.ts` checks the whole tree, not the diff** — a conscious departure from the diff-ratchet philosophy the other three share, argued in the file's own header (the tree is clean, so a diff-only net would let files drift back). Do not port a diff-ratchet over it as a "fix".
- **`modules/rule/` and the `rule_*` MCP tools are product** — Hebrew-calendar occasion rules, nothing to do with the canon rulebook. Same for `modules/{member,org,ledger,donation,billing,occasion,calendar,schedule,scheduled-message,zmanim,messaging,pdf}` and `packages/luach`.
- **`modules/agent/` is the product AI assistant** (chat, skills, widgets, vision, consent, proposals, model catalogue) — the shul-admin-facing feature, not shared infrastructure. Do not scan it as a portable AI layer, and do not port starship's `Infrastructure/AI` into it. Its `agent.models.ts`/`agent.catalogue.ts` model-registry pattern is the one part that could be argued portable; treat that as a proposal, not a scan hit.
- **All worktrees deliberately share ONE Postgres.** `docker-compose.yml` fixes `name: adanim` + `container_name: adanim-postgres` + `5432:5432` precisely so that every checkout of the repo addresses the same database, and `.env` is symlinked so every worktree literally reads one `DATABASE_URL`. This is a choice with a whole ring of diagnostics around its single failure mode (`announce-unpushed.ts` warns the writer at `db:migrate`; `check-ledger.ts` distinguishes "another worktree applied this" from a corrupt row; `test-preflight.ts` catches the reader as a preload; `check-migrations.ts` bans `ADD COLUMN NOT NULL` without a default naming this exact reader). Ports and dev servers are shared too, explicitly not automated. Do **not** "fix" this into per-worktree databases, and do not read it as adanim being behind — it is the opposite choice from starship's, made on purpose.
- **`scripts/merge.ts` (`bun run merge`) does a bare `git merge --ff-only` with no PR and no review gate**, which is coherent only because adanim is single-branch and commits straight to local `master`. Its **migration-lineage fork check is portable; the merge command is not** — dropped into a repo with a pre-push review gate it would route around it. Same reasoning applies to branching worktrees from local `HEAD`: correct there (work is pushed rarely, so local HEAD is the more complete ref), wrong anywhere with an integration branch.
- **Vendored skills with `skills-lock.json`** — adanim pins agent skills in `.agents/skills/` behind a lockfile. None of the other three do this; it is a candidate to port outward, not a drift to correct.

## Process differences

- YouTrack: starship uses the janus instance (`youtrack-starship` server); alephbeis uses modstudio (`youtrack-alephbeis`); stopal and adanim do not use YouTrack.
- **Adanim is single-branch and has no CI.** Origin is `github.com/modstudio/adanim.git` (added since 2026-07-31) and the default branch is `master` — there is no `develop`, so no feature→develop→master train; doctrine #6's squash-merge reasoning applies directly to `master` and `refs.json` SHAs must be ancestors of `origin/master`. There is still no `.github/`, so branch protection and CI-gated release have nowhere to attach yet; a CI port is now *possible* (it wasn't before the remote) and is the biggest open gap.
- **Adanim task keys are `ADN-*`**; its MCP server is registered as `adanim` and its tools are `mcp__adanim__*`. It was called **shulbase** until early August 2026 — treat any lingering `shulbase` reference in notes, refs, or task text as the same project.
- Rules docs: same core set (system-prompt, core-workflow, coding-style, architecture, testing, context/ops) but numbered/named differently per project — port rule CONTENT changes, keep each project's file naming.
- Local env refresh after a pull: starship's `scripts/sync/main` exposes `--refresh` (full local rebuild without DB restore: git, docker-up, composer/npm gated on lockfile change, migrate, cache-clear) and `--all` (that + db-restore), plus a `.githooks/post-merge` hook that auto-runs only the `ORIG_HEAD..HEAD`-changed steps. stopal already covers this via post-checkout/merge hooks that install+migrate; alephbeis has no equivalent (its `TestDbRefresh` is test-DB only). Port to alephbeis = add the flags/hook; port to stopal = adapt to the existing hooks, don't duplicate. `ide-helpers` is intentionally excluded from starship's composite (its `-M` rewrites tracked models).
