# Shared Doctrine — what ports, and to what standard

Two jobs: (1) the **portability test** that decides whether a change is a port candidate at all; (2) the **settled cross-project best practices** every port conforms TO. Update this file the moment a new doctrine decision is made. (Per-project uniques and translation notes live in `differences.md`.)

## The portability test (apply FIRST, to every candidate change)

A feature ports when it belongs to the **project-management / system-management layer** — the developer-and-agent-facing subsystem that all four projects deliberately share. It does NOT port when it belongs to the **product domain** — what the app does for its users.

**Portable (project-managed + system-management):**
- Task management: tasks, task documents, comments, activity, watchers, links/hierarchy
- Workflows: definitions, steps, modes, compose, prompts
- Rulebook / rules canon (DB-sourced rules, hydrate/sync tooling, session-rules hooks)
- Knowledge base (articles, search, `@link` citation plumbing) — the KB *system*, not its business content
- Code metrics
- Monitoring & ops reporting: Beacon-style failure monitoring + auto-filed issue queues, error/exception tracking (Nightwatch wiring), health/ops dashboards and reporting (NOT business reports — starship's Reports domain is product)
- MCP server infrastructure: auth, audit logging, rate limiting, token minting, tool registration/plumbing, transports
- Agent ops tools: logs, queue, database query, telescope, artisan/schedule/cache/migrations, server health
- Dev experience: multi-instance/parallel-checkout setup (new-instance scripts, compose overrides, instance-info), app config systems (in-app encrypted config, env conventions), CI pipelines + ratcheted quality gates + pre-commit hooks, agent-canon sync tooling (rules hydrate, per-tool config generation), release tooling

**Never ported (product domain):**
- starship: supply chain — orders, inventory, shipments, purchasing, RevOps, IMS, Import, supplier API
- stopal: the customer-facing product — payments/Stripe, auth product features, client apps
- alephbeis: curriculum, learning content, student/teacher features

Gray zone: ops frontend (task boards, workflow editors). The *capability* ports; the implementation is re-expressed per stack (see the stack mapping in `differences.md`) — never a 1:1 UI copy into a Laravel app.

## Authoritative best practices (settled doctrine — ports conform to these)

These are decided. A port that would violate one needs the user's explicit sign-off, and a source project that violates one is itself a port candidate (bring it INTO compliance).

1. **DB is the source of truth for agent-operational data** (rules, workflows). Git holds only a generated, read-only mirror, exported one-way (starship's hydrate/canon-sync pattern). Mirrors are never hand-edited; fresh environments bootstrap from the mirror; there is no two-way file↔DB sync. (Retires alephbeis's workflow JSON seeder as an authoring surface; porting the hydrate pattern to cover workflows in alephbeis/stopal is an open port candidate.)
2. **Quality enforcement is diff-ratcheted**: new violations fail, untouched legacy is exempt, and there is no baseline-file escape hatch to dodge a gate. Pre-commit hooks and CI run the same checks (parity is itself a guard).
3. **Task-first development**: every non-trivial change gets a task in the project's own in-app system before implementation; the task key goes in branch/commit/PR — never in source code comments.
4. **MCP tool design**: thin tool wrappers delegating to domain actions; read-only ops tools are freely exposed; destructive tools are two-step (bare call = preview, explicit `confirm: true` = execute). Every tool call surface is authenticated (sanctum/bearer) and rate-limited; audit logging of tool calls (alephbeis's McpAuditLogger pattern) is the standard, not an option.
5. **Autonomy knobs govern agent behavior per stage** (plan/implement/review/docs/canon/ship); harness permissions stay permissive — behavior policy lives in the project rulebook, not in permission prompts.
6. **Release ladder is CI-driven**: feature → develop (= staging deploy) → master (= production deploy); never deploy code over SSH; a CLI release path is allowed only with a CI-parity gate (stopal's release.sh pattern). SSH is for investigation and verification only.
7. **Multi-instance dev**: parallel checkouts namespaced deterministically (`COMPOSE_PROJECT_NAME` + port offsets by instance index); scripts never assume a single-checkout layout. **Prefer no `container_name` at all** — Compose namespaces containers from the project name, so there is no variable to leave unset and a new clone works untouched (reference: stopal). Set an explicit name *only* where deployment requires a fixed one (alephbeis's atomic swap renames `alephbeis-server` and routes cloudflared at it); then parameterise it with a documented variable whose fallback is the production name — an undocumented variable that falls back to the *shared* name silently collides with clone 0. Never **reference** a container by name: `docker compose exec <service>` resolves through the current project. Per-checkout hand-written override files are not namespacing — they are duplication that a new clone or new service silently misses. Everything else that varies per checkout is derived from that checkout: URLs from its `APP_URL`; a `-local` MCP server is registered **per project** with its URL derived from `APP_URL`, never in a global registry — a global entry can only pin one clone, and the wrong clone then answers *successfully*, which is the failure mode to design against throughout this doctrine. A diagnostic that prints per-clone values must print only what is actually bound; one that reports an unpublished port is worse than none.
8. **App config is DB-backed, encrypted, runtime-resolved** with typed keys and an environment cascade; secrets never in git; Claude-facing credentials live in `~/.claude/.env`.
9. **Agent canon files are generated**: per-tool configs (.claude/, .cursor/, root AGENTS.md…) are produced by `scripts/sync` from `.agents/` — never hand-edited.
10. **Comments state the non-obvious why only** — the current invariant, never history ("used to…", "PR N changed…"), no development commentary, and no provenance of any kind: no issue keys, tracker URLs, or internal doc/brand names (provenance lives in commits/PRs/tracker). Enforced by ratcheted guards (reference implementation: starship's `check-comment-hygiene.php` + `check-task-keys-in-source.php`).
11. **Tests must be falsifiable, never dogmatic** — starship's `08-testing` doctrine is canonical for all three projects: test hidden business logic per the litmus ("if someone changed this subtly wrong, would anything fail?"); assert effects, not interactions; the three smells (vacuous / change-detector / over-isolated) are flagged on sight; no coverage maximalism, no test-per-change rules. Don't-test list includes: glue/delegation, what the type system proves, and **one-time data migrations/backfills** (they run once against prod-shaped data no fixture matches — verify by lint, review, and read-only pre-flight queries instead; schema migrations with ongoing read/write behavior keep their handler tests).
12. **Clean cut — no legacy residue.** A refactor/migration isn't done until the tree is fully migrated: no deprecated columns, dual-writes, compat shims, superseded paths, or redundant identity maps left behind. Transitional steps are fine mid-flight, but the debt is tracked and closed by a follow-up increment that *deletes* the old path. (Release-time safety for the deletion itself is the migration-safety gate.)
13. **The domain model is independent of source systems.** Domain symbols (columns, classes, events, DTO fields) are never named after a source/vendor system; those names live only inside that system's integration/import layer, and values cross the boundary as neutral fields (`shipLocationId`, not `acctivateLocationId`). Legacy source-named columns are grandfathered under the diff-ratchet.
14. **Canon codifies the best convention on merit, never the merely-dominant one.** When turning existing code into a rule, pick the best variant (intent, modern idiom, determinism) even if another form is more common; where canonical ≠ dominant, new code ratchets to the better rule and the dominant form converges when touched.
15. **Design tokens only, everywhere.** Frontend styling uses design tokens (`$space-*`, `var(--*)`) — never hardcoded hex colors, pixel values, or chrome-aware magic offsets in new/changed lines. Enforced by ratcheted guards (reference: starship `check-design-tokens.sh`).
16. **Fix the primitive, never wrapper-patch.** When a design-system component's layout looks off, read the component's source and restructure the markup so the primitive can do its job — no wrapper divs, margin-gap overrides, or explanatory CSS at the call site. If the primitive itself misbehaves, fix the component.
17. **Everything CI runs must run exactly the same locally.** Every CI check exists locally with the identical command (pre-commit hook and/or repo scripts, run from repo root); when CI gains a step, the local mirror lands in the same PR. Fix locally, push once — never push-fix-push against CI.
18. **Behavior is encoded in canon and workflows, never in Claude memories.** The rules DB and workflow DB are the only carriers of "when X, do Y" — they reach every agent session, every tool, every machine, and they port between projects. Claude memories hold only facts, gotchas, and references (container names, framework quirks, incident details). A behavioral correction given in-session gets proposed into the project's canon/workflow (via the KB/canon review gate), not parked in memory.
19. **Sync tooling shape: git-first, `--all`, defaults + sparse overrides.** The project sync script runs git sync FIRST (every later step executes from the fresh checkout; re-exec once if the pull updated the sync scripts themselves) and offers an `--all` flag for the full sweep (git, agents, mcp, db-restore — auto-starting Docker when needed). Its config resolves in layers: a **tracked defaults file** (`sync-config.defaults.yml`) is live config, and a **gitignored overrides file** (`sync-config.overrides.yml`) carries only the keys a dev deliberately changes — key-present wins in both directions (an explicit `false` beats a `true` default), absent keys resolve from defaults, so new options take effect without hand-merging. First run writes a comment-only override stub and continues on defaults (no "edit and re-run" stop). No legacy-name compat shims — old config filenames are cut clean (doctrine 12). A status command shows every resolved value labeled override/default. (Reference implementation: starship `scripts/sync/`.)
20. **Ported work carries no source-project trace.** Task titles, descriptions, and the ported code itself — identifiers, comments, strings, config keys — never name the other project, its commits, or its paths. Each project stands on its own; cross-project references muddy its codebase and task history with names that mean nothing inside that project. Source pointers live only in the port-feature skill's `refs.json` ledger, reached via a single neutral `Porting reference:` line in the pending task (removed once the task is implemented).
21. **Review depth is tiered to the change; the review gate never is.** Every change is reviewed — that gate is mandatory at every tier and a local/ad-hoc check never substitutes for it. What scales is review *depth*: how many independent reviewers, along how many distinct lenses (correctness/security, design, quality, tests, dead-code, efficiency, surface specialists), with how much adversarial verification. Match depth to **risk × size**, classifying by the **higher** axis and defaulting upward when unsure — risk (money, auth, migrations/backfills, deletions/cutovers, shared contracts, security paths) is judged by surface touched, not line count, so a tiny high-risk diff still gets deep review; a large mechanical/additive/generated diff stays shallow. The ladder: **Tier 0 (trivial** — docs/config/comment/formatting or small additive no-logic): automated gates + a single self-review across the core lenses, no independent reviewers. **Tier 1 (low-risk** — small self-contained behavior, no logic branching / external input / data / money / auth / shared-contract change; faithful ports land here): gates + one-to-two independent reviewers on the actual surface. **Tier 2 (standard**, the default when unsure — any real logic, behavior change, shared-component change, query/persistence change): full multi-lens independent review + **adversarial verification** (each finding independently re-derived from the code, never accepted on say-so; "real problem, wrong fix" is corrected, not discarded). **Tier 3 (high-risk** — irreversible/wide-blast-radius): Tier 2 + an independent second opinion from outside the primary reviewer pool (different model/team/person) + heightened verification (reproduce the failure the change prevents; confirm the rollback path). Invariants at every tier: critical/unfixable findings always surface and stop the ship (re-tier up on the spot); findings are verified not trusted; the run is recorded (tier, reviewers, outcome) for reviewer calibration; and the chosen tier + its one-line reason travel with the change so a too-low classification can be challenged. This is the concept; each project's review workflow implements it in that project's own terms.
